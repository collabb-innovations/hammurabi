## Context

Hammurabi 0.1.0 shipped 2026-06-08 and saw immediate dogfooding via `hook.`/continuum:

- **Continuum#248** — first eval-driven bundle authored against 0.1.0. A 5-round adversarial review (Codex) surfaced eight authoring footguns; five became issues #7–#11.
- **Continuum F-326 (today)** — `mood-board-search`'s blessed baseline contains 2 legitimately-failing fixtures (EVAL-ES-015 / EVAL-ES-019, faithful migration from a bespoke suite). Repo-wide `hammurabi-check evals/` therefore exits 1 with zero regressions, breaking continuum's `/ship` eval gate. Issue #12.

Of those six issues, three are bug-class or docs and can ship together as a patch with no schema change:

| # | Item | Why now |
|---|---|---|
| **12** | `hammurabi-check` exits 1 forever for baselines with legit reds | Breaking real CI today; teams are working around it by quarantining fixtures (anti-pattern) |
| 8 | Cryptic mid-scoring failure on unresolved imports | ~30 lines, prevents the exact trap from continuum round 4 |
| 11 | Author-guidance docs (import the contract; match validator config; declare deps) | Codifies the round-1–4 mistakes; pairs naturally with #8 |

The other three (#7, #9, #10) deserve their own release(s) — they touch schema or require design rounds. Out of scope here.

## Decisions

1. **Exit semantics change is a policy fix, not an API break.** The current behavior ("exit 1 if any fixture currently fails") was wrong — it makes `hammurabi-check` unusable in any repo whose honest baseline isn't 100% green. Document in `CHANGELOG.md` under "Changed (policy)" without bumping major. Both `hammurabi-run` and `hammurabi-check` change to the new contract.

2. **No `Report` schema change.** The known-fail vs new-fail distinction is computed at the CLI layer from `(currentReport, baselineReport)` diff. Adds zero fields to the on-disk schema. Symmetric treatment for "improvements" (was failing, now passing) — printed to stdout, not stored in `ReportSummary`. If we later want it on disk, that lands in 0.2.0 alongside #9's `applicable` field as one cohesive report-shape bump.

3. **Preflight lives in `src/runner/preflight.ts`, called from both CLI bins.** Not in `loadBundle()` — loading is parse-and-validate (no dynamic imports), preflight is import-time-resolution (dynamic). Different concerns. Keeps the library `run()` path silent (callers like Knack that already manage their own imports don't pay the preflight cost twice). `--no-preflight` escape hatch.

4. **Docs land in three surfaces in one PR**: `README.md` (a new "Authoring guidance" section), `commands/hammurabi.md` (Step 1 gets a "before you start" checklist), and a new `docs/authoring-guide.md` (deep-dive). The slash command updates make the guidance flow into every new bundle authored after the patch ships.

5. **No new dependencies.** All three issues are addressable with stdlib + existing types.

## Issue #12 — Baseline-aware exit semantics

### Current behavior (broken)

`src/cli/check.ts:112-119` (`exitCode`):
```ts
function exitCode(outcomes: BundleOutcome[]): 0 | 1 | 2 {
  if (outcomes.some((o) => o.error)) return 2;
  const bad = outcomes.some((o) => {
    const s = o.report!.summary;
    return s.failed > 0 || s.errored > 0 || (s.regressions?.length ?? 0) > 0;
  });
  return bad ? 1 : 0;
}
```

`src/cli/run.ts:99-102`:
```ts
const hasFailure =
  report!.summary.failed > 0 || report!.summary.errored > 0;
const hasRegression = (report!.summary.regressions?.length ?? 0) > 0;
process.exit(hasFailure || hasRegression ? 1 : 0);
```

A fixture failing identically in the committed baseline contributes to `summary.failed` and therefore exit 1, forever.

### New contract

Exit 1 fires on, and only on:
- **New failures** — fixture passed in baseline, fails now (or has no baseline entry and fails now)
- **Regressions** — score dropped > `regressionThreshold` (existing behavior, unchanged)
- **Errors** — fixture errored in execution or judging (unchanged; errors are infrastructure problems, never "known")

Baselined-still-failing fixtures report as `known-fail (baselined)` warnings in stdout and contribute to a `knownFailures` count in the combined `check-report.json`. They do NOT contribute to the exit code.

Baselined-failing fixtures that now pass surface as `improvement: re-bless with --update-baseline?` prompts in stdout. Do not contribute to exit code.

### Implementation

New helper `src/cli/baseline-diff.ts`:

```ts
import type { Report } from "../schema/report.js";

export interface BaselineDiff {
  newFailures: string[];          // fixture ids that passed in baseline, fail now (or no baseline)
  knownFailures: string[];        // fixture ids failing in both baseline and current
  improvements: string[];         // fixture ids failing in baseline, passing now
}

export function diffAgainstBaseline(
  current: Report,
  baseline: Report | undefined,
): BaselineDiff {
  const baselineFailing = new Set(
    baseline?.results.filter((r) => !r.passed).map((r) => r.fixtureId) ?? [],
  );
  const newFailures: string[] = [];
  const knownFailures: string[] = [];
  const improvements: string[] = [];

  for (const r of current.results) {
    if (!r.passed) {
      (baselineFailing.has(r.fixtureId) ? knownFailures : newFailures).push(
        r.fixtureId,
      );
    } else if (baselineFailing.has(r.fixtureId)) {
      improvements.push(r.fixtureId);
    }
  }
  return { newFailures, knownFailures, improvements };
}
```

`src/cli/check.ts` changes:
- `runBundle` retains the baseline it loaded so it's available for the diff (return it on `BundleOutcome` alongside `report`).
- `exitCode` switches to: `outcomes.some(o => diff(o).newFailures.length > 0 || (o.report!.summary.regressions?.length ?? 0) > 0)` plus the existing errored-bundle check for exit 2.
- `formatSummary` prints `K known-fail / N improvement` annotations after the bundle line and a top-level "❍ N improvement(s) — consider re-blessing baselines" footer.
- `writeCombined` adds `knownFailures: number, newFailures: number, improvements: number` to each bundle entry in `check-report.json`.

`src/cli/run.ts` changes:
- After computing `report`, do `diffAgainstBaseline(report, flags.baseline)`.
- Exit logic switches to: `(newFailures > 0 || regressions > 0 || errored > 0) ? 1 : 0`.
- Stdout summary block surfaces known-fails and improvements (same vocabulary as `check`).

### Tests

`tests/baseline-diff.test.ts` (new):
- empty baseline → all failing fixtures classified as newFailures
- fixture failing in both → knownFailures
- fixture passing in baseline, failing now → newFailures
- fixture failing in baseline, passing now → improvements
- no baseline at all → newFailures = all currently failing
- mixed: 1 known-fail + 1 new-fail + 1 improvement + 1 steady-pass → counts correct

`tests/check.test.ts` (extend):
- bundle with baseline that contains 2 failing fixtures + run reproducing those 2 failures → exit 0
- same bundle + one additional new failure → exit 1
- same bundle + one of the 2 baselined fails now passes → exit 0, improvement printed
- no baseline + any failure → exit 1 (parity with no-baseline-discovered case)

## Issue #8 — Import-resolution preflight

### What we're catching

Continuum round 4 (`hook.`): evaluator imported bare `ajv`; bundle directory wasn't an installed package; `ajv` resolved only via incidental hoist to the wrong major in dev, would fail entirely in a fresh install. Two import surfaces in a bundle:

1. **Target** — when `spec.frontmatter.target.kind === "function"`, `target.module` must resolve.
2. **Code evaluators** — every `criterion.evaluator.kind === "code"`, `criterion.evaluator.module` must resolve.

Both fail today inside `executeFixture` / `scoreCodeCriterion` mid-scoring with `Cannot find module '...'` and no context about which criterion / bundle.

### Implementation

New file `src/runner/preflight.ts`:

```ts
import type { Spec } from "../schema/spec.js";
import type { Rubric } from "../schema/rubric.js";

export interface PreflightFailure {
  bundlePath: string;
  source: string;     // e.g. "spec.target.module" or "rubric.criteria[2].evaluator.module"
  module: string;
  error: string;
}

export async function preflightImports(
  spec: Spec,
  rubric: Rubric,
  bundlePath: string,
): Promise<PreflightFailure[]> {
  const failures: PreflightFailure[] = [];
  const targets: { source: string; module: string }[] = [];

  if (spec.frontmatter.target.kind === "function") {
    targets.push({
      source: "spec.target.module",
      module: spec.frontmatter.target.module,
    });
  }
  rubric.criteria.forEach((c, i) => {
    if (c.evaluator?.kind === "code") {
      targets.push({
        source: `rubric.criteria[${i}] (${c.id}).evaluator.module`,
        module: c.evaluator.module,
      });
    }
  });

  for (const { source, module } of targets) {
    try {
      await import(module);
    } catch (e) {
      failures.push({
        bundlePath,
        source,
        module,
        error: (e as Error).message,
      });
    }
  }
  return failures;
}

export function formatPreflightFailures(failures: PreflightFailure[]): string {
  return failures
    .map(
      (f) =>
        `  ${f.bundlePath}\n    ${f.source}: cannot resolve '${f.module}'\n    ${f.error}`,
    )
    .join("\n");
}
```

CLI integration:
- `src/cli/check.ts` `runBundle`: after `loadBundle(specPath)`, before `run(...)`, call `preflightImports(spec, rubric, specPath)`. If failures, treat as `outcome.error` (exit 2) with the formatted message. Add `--no-preflight` flag for symmetry with `--no-baseline`.
- `src/cli/run.ts`: same insertion after `loadBundle` and before `run`. Adds `--no-preflight` flag.
- Library `run()` does NOT call preflight (callers like Knack manage their own import resolution).

### Tests

`tests/preflight.test.ts` (new):
- spec with `target.kind === "free-form"` → 0 failures (no target module to resolve)
- spec with `target.kind === "function"`, module exists → 0 failures
- spec with `target.kind === "function"`, module doesn't exist → 1 failure with `source === "spec.target.module"`
- rubric with 2 code-evaluator criteria, both modules exist → 0 failures
- rubric with 1 code criterion pointing at unresolvable module → 1 failure with criterion id in `source`
- combined: bad target + 1 bad criterion → 2 failures, both with distinct `source`s

## Issue #11 — Author-guidance docs

### README additions

Add a new top-level section between "Schema" and "The `eval` block":

```markdown
## Authoring guidance

Three patterns that consistently bite first-time bundle authors. Adopt them
before you author the rubric.

### Import the contract — never re-encode it

If your target produces output conforming to a schema, JSON spec, or function
signature, **your evaluator should import the same definition the target uses**.
Hand-copying the key list, type shape, or validation rules into the evaluator
guarantees drift the first time the target changes. Common form of the bug: a
`requiredKeys` array drifts out of sync with the source `*.schema.json`, and
the gate silently rots.

### Mirror your production validator's library and config

If the eval mirrors a production validator (ajv, zod, joi, …), pin the **same
major version** the production code uses, and apply the **same config**
(`formats`, `coerceTypes`, `strict`, etc.). An ajv 8 evaluator gated against
ajv 6 production code is not the same gate.

### Bundles using external deps must be installed packages

A bundle directory that imports `npm` packages must contain a `package.json`
with the deps declared. Relying on "the parent project happens to hoist it"
breaks the documented `hammurabi-check evals/` use case the moment the bundle
runs in a CI workspace or a different repo. Hammurabi's preflight (since
0.1.1) catches this, but the root cause is the missing `package.json`.
```

### `commands/hammurabi.md` changes

After "Step 1: Read the spec", insert "Step 1.5: Bundle hygiene checklist":

```markdown
## Step 1.5: Bundle hygiene checklist

Before writing the rubric, confirm the following with the user (one batched
`AskUserQuestion` round):

1. **Does the target produce output against a documented contract** (JSON
   schema, TS type, OpenAPI spec)? If yes, locate it. We'll import it directly
   in code-scored criteria — we do not re-encode contracts.
2. **Will this eval mirror a production validator?** If yes, capture the
   library + version + config used in production. The evaluator must match.
3. **Does the bundle directory have a `package.json` with declared deps?** If
   the rubric will use external deps in code-scored criteria and there's no
   declared dependency, the eval will break on `hammurabi-check`.

If any answer reveals a gap, fix it before continuing. These three patterns
are the dominant authoring footguns (continuum round 1–4 evidence).
```

Long-form expansion of the three patterns with concrete examples, anti-patterns from continuum#248 (anonymized), and remediation recipes. README links to it. Ships in the npm package via `files` (add `"docs/"`).
